# Commit signing

Mogplex can sign the commits it makes on a user's behalf. This document
describes how it works today, what it does not cover, and how to enable it.

## The problem this solves

Before this feature, commits made in Mogplex were *attributed* to the acting
user but never *signed*:

- `lib/sandbox/git-author.ts` resolves the commit author from the user's
  GitHub identity (`<githubUserId>+<login>@users.noreply.github.com`) and
  exports `GIT_AUTHOR_NAME` / `GIT_AUTHOR_EMAIL` / `GIT_COMMITTER_NAME` /
  `GIT_COMMITTER_EMAIL`.
- Nothing in the repository configured `gpg.format`, `user.signingkey`, or
  `commit.gpgsign`, and no key material existed anywhere.

The result on GitHub: no "Verified" badge (or "Unverified" under vigilant
mode), and a push is rejected outright by any branch protection rule or
ruleset that requires signed commits.

## How signing works

Git signs with an SSH key through `gpg.format=ssh` (git >= 2.34), which
shells out to `ssh-keygen`. Mogplex therefore:

1. Gives each user an Ed25519 SSH signing key (generated by Mogplex or
   imported by the user).
2. Stores the private key encrypted with AES-256-GCM.
3. Writes the private key (mode 0600) and a global gitconfig into every
   sandbox that user works in.

The gitconfig the sandbox receives:

```
gpg.format = ssh
user.signingkey = $HOME/.mogplex/signing/id_ed25519
commit.gpgsign = true
tag.gpgsign = true
```

Because `commit.gpgsign` is set globally inside the sandbox, every commit the
agent, the harness, the workspace Commit button, the PR autofixer, or the
terminal makes is signed — one flip, no per-path work.

The signed identity is the same identity the commit is attributed to: the
global `user.name` / `user.email` and the `GIT_AUTHOR_*` environment both come
from `resolveSandboxGitAuthor`. A signature over a different author would be
a bad user experience, so the two are always written together.

## Enabling it

### 1. The deployment needs an encryption secret

```
MOGPLEX_COMMIT_SIGNING_KEY_ENCRYPTION_KEY=$(openssl rand -base64 32)
```

Without this variable the feature is **off**: the settings screen reports
signing as unavailable, no key can be stored, and no key is ever written to a
sandbox. Everything else in Mogplex keeps working — the failure is scoped to
commit signing only.

### 2. The user creates a key

**Settings -> Commit Signing** (personal scope):

- **Generate a signing key** — Mogplex creates an Ed25519 key.
- **Import an existing private key** — paste an *unencrypted* OpenSSH private
  key (`-----BEGIN OPENSSH PRIVATE KEY-----`). Passphrase-protected keys are
  rejected: a sandbox has no way to answer a passphrase prompt.

The private key is encrypted with AES-256-GCM (key derived with SHA-256 from
`MOGPLEX_COMMIT_SIGNING_KEY_ENCRYPTION_KEY`) before it is written to
`commit_signing_keys`. It is never returned to the browser, never logged, and
never included in an error message.

### 3. The user registers the public key with GitHub

This is a separate, explicit action ("Register with GitHub"), because
GitHub's signing-key endpoint needs a scope Mogplex's OAuth grant does not
carry by default.

- Mogplex calls `POST /user/ssh_signing_keys` with the user's OAuth token.
  That endpoint needs the `write:ssh_signing_key` scope.
- If the token has the scope, the key is registered and commits show as
  **Verified**.
- If the token is missing the scope, or the user has no OAuth token (App-only
  GitHub auth), the platform cannot register the key. Mogplex says so and
  shows the public key, which the user can paste into
  **GitHub -> Settings -> SSH and GPG keys -> Signing keys**.

`POST /user/keys` is *not* used: that is the list of authentication keys.
GitHub does not treat commits signed with an authentication key as verified.

To make automatic registration work for everyone, add `write:ssh_signing_key`
to `GITHUB_OAUTH_SCOPES` in `lib/github-oauth.ts`. That widens the OAuth
grant, so it is an operator decision, not a default.

### What GitHub shows

| Situation | GitHub shows |
| --- | --- |
| No signing key configured | Nothing — commits are unsigned |
| Key configured, not registered with GitHub | "Unverified" (signed, but GitHub has no public key to check it against) |
| Key configured and registered with GitHub | **Verified** |
| Repository uses vigilant mode | "Unverified" for keys GitHub does not know, even for registered keys of other users |

## Which commits are signed

Signed (they all happen inside the user's sandbox, with the global gitconfig
in place):

- Agent commits made through the exec route
- The workspace Commit button (`/api/sandbox/[id]/changes`)
- Harness deliveries (Slack, Claude Code, ACP)
- The PR autofixer
- Terminal commits

Not signed, by design:

- **Merge commits created by GitHub.** GitHub signs those itself when the
  repository requires it.
- **Commits the platform creates outside a sandbox.** `lib/git/post-merge-cleanup.ts`
  inspects and reports on a merged branch; it does not create commits.
- **Tags created outside the sandbox.** `tag.gpgsign = true` covers tags made
  inside a sandbox.

## Failure behaviour

Setup errors are reported without stopping workspace launch. Once signing is enabled, Git can still fail if its key or configuration is changed.

- **No key configured:** the sandbox is untouched. Behaviour is byte-for-byte
  what it was before the feature existed — unsigned commits, no prompts, no
  errors.
- **Key material missing, corrupt, or unreadable:** the setup script refuses to
  enable signing (`ssh-keygen -y` fails), the sandbox stays unsigned, and the
  platform logs a warning.
- **Sandbox git too old, or no `ssh-keygen`:** the sandbox stays unsigned and
  the platform logs a warning. Git below 2.34 does not understand
  `gpg.format=ssh`.
- **A command fails:** the setup shell removes staging material on exit and
  clears failed managed signing configuration. Transport failures are reported
  without including provider error text; a disconnected sandbox may retain
  files until cleanup or destruction.

The rule everywhere: a half-configured sandbox is worse than an unsigned
sandbox, because `commit.gpgsign = true` with a broken key makes *every*
commit fail.

## Security notes

- **The agent can read the key.** The agent runs arbitrary commands inside
  the sandbox, and the signing key has to be on the sandbox filesystem for git
  to use it. A prompt-injected agent could copy the key out. The key is
  scoped to the user who owns the sandbox, so the blast radius is "that
  user's identity can sign commits".
- **The agent can also break signing.** `commit.gpgsign = true` is a global
  git setting: if the agent deletes the key file, every later commit in that
  sandbox fails instead of falling back to an unsigned commit. That is a
  deliberate trade-off — a silently unsigned commit is harder to notice than
  a failing one — and the user can recover it by restarting the workspace.
- **Snapshots.** The private key is removed from a sandbox before the sandbox
  is captured into a workspace snapshot
  (`app/api/sandbox/[id]/restart/_lib/legacy-snapshot.ts`). A cleanup failure
  blocks that capture. The restarted sandbox gets the key back from the
  encrypted store. After a failed capture, the platform restores signing when
  the provider confirms the workspace is still running; it never wakes a
  stopped sandbox just to restore a key.
- **Persistent sandboxes** keep the key on disk, including provider-managed
  pause snapshots. These are private workspace state, not shared baselines.
  Shared repository baselines are built in a separate ephemeral sandbox
  (`lib/repo-snapshot-build.ts`) that never installs a user signing key.
- **Rotation.** Removing the key in Settings deletes only the encrypted stored
  key. Fresh workspaces no longer install it. Existing or resumed workspaces
  can retain their old copy; remove its trust on GitHub separately. Keys
  already pushed stay signed, and their signature stays verifiable for the
  public key that was registered with GitHub — revoke that key on GitHub too
  if the old key must stop being trusted.
- **Not a secret manager.** The key protects the *user's* GitHub identity, not
  Mogplex's own credentials.

## Where the code lives

| File | Purpose |
| --- | --- |
| `lib/commit-signing/key-material.ts` | OpenSSH Ed25519 key generation, parsing, fingerprinting |
| `lib/commit-signing/secret-box.ts` | AES-256-GCM encryption at rest |
| `lib/commit-signing/storage.ts` | The `commit_signing_keys` table |

| `lib/sandbox/commit-signing.ts` | Writes the key and the gitconfig into a sandbox |
| `lib/sandbox/collection/_lib/provisioning.ts` | Calls the setup on every sandbox launch |
| `lib/harness/_lib/setup.ts` | Calls the setup for harness runs |
| `app/api/settings/commit-signing/route.ts` | Settings API |
| `app/(dashboard)/[scope]/settings/_components/commit-signing-section.tsx` | Settings UI |
| `neon/migrations/20261115090000_commit_signing_keys.sql` | Schema |

The sandbox code is provider-agnostic on purpose: `lib/sandbox/commit-signing.ts`
never imports `@vercel/sandbox`.

## Open product decisions

1. Should the OAuth grant include `write:ssh_signing_key` by default, or
   stay opt-in with manual paste as the fallback? (Recommended: opt-in.)
2. Should signing be per-user only, or per-team as well? Team repositories
   often have rulesets that require signed commits, and a team key would need
   its own rotation and ownership rules.
3. Should the platform sign merge commits it creates? Today GitHub does.
